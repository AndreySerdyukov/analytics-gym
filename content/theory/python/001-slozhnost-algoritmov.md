## Зачем это нужно

Сложность – это язык, на котором обсуждают решения. Фраза «наивно O(n²), можно свести к O(n)
через хеш-таблицу» – это буквально 70 % содержания алгоритмического собеседования. Пока ты не
умеешь оценивать сложность своего кода за 5 секунд, ты не можешь ни выбрать подход, ни объяснить,
почему он лучше.

Хорошая новость: это не математика. Это подсчёт вложенных циклов плюс десяток фактов, которые
надо помнить.

## Что такое O-большое

**O(f(n)) – это ответ на вопрос: как растёт время работы, когда вход растёт.**

Не «сколько секунд», а «во сколько раз дольше, если вход станет в 10 раз больше».

| Сложность | Вход вырос в 10 раз → время выросло в | Пример |
|---|---|---|
| O(1) | не изменилось | взять `arr[5]`, `d[key]` |
| O(log n) | +3 «шага» (почти не изменилось) | бинарный поиск |
| O(n) | 10 раз | один проход по массиву |
| O(n log n) | ~13 раз | сортировка |
| O(n²) | 100 раз | двойной вложенный цикл |
| O(2ⁿ) | астрономически | перебор всех подмножеств |

Два правила, которые упрощают всё:

1. **Константы отбрасываем.** `3n + 100` → O(n). Разница между 3n и n – это вопрос оптимизации
   на 20 %, а O-нотация про порядки.
2. **Оставляем только старшее слагаемое.** `n² + 1000n` → O(n²). При больших n `n²` съедает
   всё остальное.

## Как считать: практический алгоритм

### Правило 1. Последовательные блоки – складываются, берём максимум

```python
def f(arr):
    total = 0
    for x in arr:            # O(n)
        total += x
    for x in arr:            # O(n)
        print(x)
    return total
# O(n) + O(n) = O(2n) = O(n)
```

### Правило 2. Вложенные циклы – перемножаются

```python
def has_duplicate_pair(arr):
    for i in range(len(arr)):        # n раз
        for j in range(len(arr)):    # × n раз
            if i != j and arr[i] == arr[j]:
                return True
    return False
# O(n * n) = O(n²)
```

Даже если внутренний цикл идёт не с нуля:

```python
for i in range(n):
    for j in range(i + 1, n):   # в среднем n/2 итераций
        ...
# n * n/2 = n²/2 → O(n²)
```

Треугольный обход – всё равно O(n²). Константу ½ отбрасываем.

### Правило 3. Разные переменные – разные буквы

```python
for a in arr1:      # len = n
    for b in arr2:  # len = m
        ...
# O(n * m), а НЕ O(n²)
```

Это частая ошибка на собесе. Если массивы разные – пиши `O(n·m)`.

### Правило 4. Деление пополам – это log

```python
def binary_search(arr, target):
    lo, hi = 0, len(arr) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        ...
# область поиска: n → n/2 → n/4 → ... → 1
# число шагов = log₂(n)  →  O(log n)
```

Мнемоника: **если на каждом шаге размер задачи делится на константу – это log n.**
Для n = 1 000 000 это всего 20 шагов.

### Правило 5. Скрытая сложность вызовов

Самая частая ошибка новичка – считать встроенные операции бесплатными.

```python
def f(arr):
    result = []
    for x in arr:               # n раз
        if x in result:         # ⚠️ поиск в списке – O(len(result))!
            continue
        result.append(x)
    return result
# O(n²), хотя цикл всего один!
```

Тот же код с множеством:

```python
def f(arr):
    seen = set()
    result = []
    for x in arr:
        if x in seen:           # → O(1)
            continue
        seen.add(x)
        result.append(x)
    return result
# O(n)
```

**Правило: каждый раз, когда пишешь `in`, `.index()`, `sorted()`, `min()`, срез или конкатенацию
строк внутри цикла – остановись и посчитай, сколько это стоит.**

## Сложность по памяти

Считается так же, но про дополнительно выделенную память.

```python
def f(arr):
    total = 0            # O(1) – одна переменная
    for x in arr:
        total += x
    return total
# память: O(1)

def g(arr):
    doubled = [x * 2 for x in arr]   # новый список длины n
    return doubled
# память: O(n)
```

Важные тонкости:

- **Вход не считается.** Если тебе дали массив длины n, память O(1) означает «я не создал ничего
  дополнительного размера n».
- **Рекурсия жрёт память на стек.** Рекурсия глубины n – это O(n) памяти, даже если внутри ничего
  не создаётся. Обход дерева DFS – O(h), где h – высота; для вырожденного дерева-«палки» это O(n).
- На собесе часто спрашивают «а можешь за O(1) памяти?» – это обычно намёк на два указателя или
  на модификацию входа на месте.

## Как выглядят типичные сложности (шпаргалка)

| Что видишь в коде | Сложность |
|---|---|
| Обращение по индексу, работа со словарём/множеством | O(1) |
| Бинарный поиск, движение по высоте сбалансированного дерева | O(log n) |
| Один проход, два указателя, скользящее окно, префиксные суммы | O(n) |
| Сортировка, куча с n вставками, `sorted()` | O(n log n) |
| Два вложенных цикла, все пары | O(n²) |
| Backtracking по подмножествам | O(2ⁿ) |
| Перебор перестановок | O(n!) |

## Амортизированная сложность (и почему `append` – это O(1))

`list.append()` формально иногда дорогой: когда внутренний буфер заполняется, Python выделяет
новый массив побольше и копирует всё туда – это O(n).

Но такое случается редко (буфер растёт в ~1,125 раза), и если размазать стоимость всех копирований
по всем вызовам, получается **O(1) амортизированно**. То есть n вызовов `append` в сумме стоят O(n).

То же самое с `dict` и `set`: одна операция – O(1) в среднем. В патологическом случае (все ключи
схлопнулись в один хеш-бакет) – O(n), но на практике это не встречается.

На собесе достаточно сказать «O(1) амортизированно» – этого хватает.

## Типичные ловушки при подсчёте

**Ловушка 1: сортировка внутри цикла**

```python
for i in range(n):
    arr.sort()      # O(n log n) на каждой итерации!
# итого O(n² log n), а не O(n log n)
```

**Ловушка 2: конкатенация строк в цикле**

```python
s = ""
for word in words:
    s += word       # создаётся НОВАЯ строка длины len(s) каждый раз
# O(суммарной длины²)
```

Правильно:
```python
s = "".join(words)   # O(суммарной длины)
```

**Ловушка 3: `list.pop(0)` и `list.insert(0, x)`**

```python
while queue:
    x = queue.pop(0)   # ⚠️ O(n) – сдвигает весь список!
# итого O(n²)
```

Правильно – `collections.deque`:
```python
from collections import deque
queue = deque(arr)
while queue:
    x = queue.popleft()   # → O(1)
```

**Ловушка 4: срезы**

```python
for i in range(n):
    sub = arr[i:]      # ⚠️ копирует, O(n)
# O(n²)
```

Срез в Python **всегда копирует**. Внутри цикла это почти всегда ошибка – работай с индексами.

**Ловушка 5: `set` внутри цикла из среза**

```python
for i in range(n):
    if len(set(arr[i:i+k])) == k:   # O(k) на каждой итерации
        ...
# O(n·k) – иногда это норм, но надо это осознавать
```

## Проверь себя

Определи сложность каждого фрагмента.

```python
# A
def a(n):
    count = 0
    i = 1
    while i < n:
        count += 1
        i *= 2
    return count

# B
def b(arr):
    result = []
    for x in arr:
        result.append(sorted(arr)[0])
    return result

# C
def c(matrix):          # matrix: n строк по m столбцов
    total = 0
    for row in matrix:
        for val in row:
            total += val
    return total

# D
def d(arr):
    seen = {}
    for i, x in enumerate(arr):
        if x in seen:
            return [seen[x], i]
        seen[x] = i
    return []

# E
def e(s):
    result = ""
    for ch in s:
        result = ch + result
    return result

# F
def f(arr):
    arr.sort()
    lo, hi = 0, len(arr) - 1
    while lo < hi:
        if arr[lo] + arr[hi] == 0:
            return True
        elif arr[lo] + arr[hi] < 0:
            lo += 1
        else:
            hi -= 1
    return False
```

<details>
<summary>Ответы</summary>

- **A → O(log n).** `i` удваивается на каждом шаге, значит шагов log₂(n).
- **B → O(n² log n).** Цикл n раз, внутри `sorted(arr)` – это O(n log n) каждый раз. Классическая
  ловушка: дорогой вызов спрятан внутри цикла.
- **C → O(n·m).** Разные размерности – разные буквы. Если сказать «O(n²)» – это неточно.
- **D → O(n) по времени, O(n) по памяти.** Один проход, словарь даёт O(1) на проверку. Это,
  кстати, решение задачи Two Sum.
- **E → O(n²).** `ch + result` создаёт новую строку длины len(result) на каждой итерации:
  1+2+3+…+n = n²/2.
- **F → O(n log n) по времени.** Сортировка доминирует: O(n log n) + O(n) двух указателей. По
  памяти O(1) дополнительно (если считать, что сортировка на месте; формально Timsort в Python – O(n)).

</details>

## Что говорить на собеседовании

Три фразы, которые стоит довести до автоматизма:

1. **После наивного решения:** «Это O(n²) по времени и O(1) по памяти. Давай подумаю, можно ли
   быстрее.»
2. **При оптимизации:** «Я разменяю память на время: заведу словарь и запомню то, что уже видел –
   получится O(n) времени и O(n) памяти.»
3. **В конце:** «Итоговая сложность – O(n log n) по времени за счёт сортировки и O(1)
   дополнительной памяти.»

Всегда называй **обе** сложности – по времени и по памяти. Многие называют только время, и это
выглядит как неполное понимание.

## Карточки

### Q: Что означает запись O(n) и почему в ней отбрасывают константы?

O-нотация описывает **порядок роста** времени работы при увеличении входа, а не абсолютное время.
`3n + 100` и `n` растут одинаково – линейно, поэтому оба записываются как O(n). Константы влияют
на реальную скорость, но не на то, как решение масштабируется, а разговор о выборе алгоритма
именно про масштабирование.

### Q: Чем O, Θ и Ω отличаются друг от друга?

`O` – верхняя оценка («не хуже чем»), `Ω` – нижняя («не лучше чем»), `Θ` – точная, когда верхняя
и нижняя совпадают. На собеседовании, говоря «алгоритм за O(n log n)», обычно имеют в виду именно
`Θ`. Формально сказать «сортировка за O(n²)» не ошибка, но собеседник услышит другое.

### Q: Какая сложность поиска элемента в list, set и dict?

В `list` – O(n): это линейный перебор. В `set` и `dict` – O(1) в среднем за счёт хеш-таблицы,
O(n) в патологическом случае, когда все ключи попали в один бакет. Замена `x in list` на
`x in set` внутри цикла – самая частая оптимизация с O(n²) до O(n).

### Q: Почему list.append – O(1), а list.insert(0, x) – O(n)?

`insert(0, x)` сдвигает все элементы вправо, чтобы освободить первую позицию – это n операций.
`append` пишет в конец уже выделенного буфера. То же самое с `pop(0)` против `pop()`: если нужна
очередь, берут `collections.deque`, у которой оба конца дают O(1).

### Q: Что такое амортизированная сложность на примере append?

Когда буфер списка заполняется, Python выделяет новый побольше и копирует всё – эта конкретная
операция стоит O(n). Но происходит она редко, и если размазать стоимость всех копирований по всем
вызовам, средняя цена одного `append` остаётся константной. Отсюда формулировка «O(1)
амортизированно»: n вызовов в сумме стоят O(n).

### Q: Какая сложность сортировки в Python и чем интересен Timsort?

O(n log n) в среднем и худшем случае. Timsort ищет в данных уже отсортированные участки и
склеивает их, поэтому на почти упорядоченных данных приближается к O(n). Быстрее чем n log n
сортировка сравнением быть не может – это доказанная нижняя граница.

### Q: Почему `for x in a: if x in b` на двух списках даёт O(n·m) и как это чинится?

Внешний цикл идёт n раз, а `x in b` для списка – линейный поиск по m элементам. Итого n·m.
Достаточно один раз построить `b_set = set(b)` (это O(m)) и проверять вхождение в него: получится
O(n + m). Ровно та же идея стоит за hash join в базах.

### Q: Что такое сложность по памяти и когда она важнее времени?

Это объём **дополнительной** памяти сверх входных данных. Важнее времени, когда данные не
помещаются в память: большие выборки, глубокая рекурсия (каждый кадр стека – это память,
рекурсия глубины n стоит O(n)) и материализация промежуточных таблиц в pandas, где несколько
копий датафрейма кладут процесс раньше, чем он успеет досчитать.

### Q: Какая сложность у бинарного поиска и при каком условии он применим?

O(log n): область поиска делится пополам на каждом шаге. Нужны два условия – контейнер
отсортирован и даёт доступ по индексу за O(1). На связном списке второе не выполняется, переход
к середине сам стоит O(n), и преимущество теряется.

### Q: Почему hash join быстрее nested loop и где аналитик встречает это на практике?

Nested loop для каждой строки одной таблицы перебирает вторую – O(n·m). Hash join один раз строит
хеш-таблицу по меньшей стороне и делает по одному O(1)-обращению на строку – O(n + m). Это тот же
механизм, что стоит за `df.merge` в pandas и за выбором плана JOIN в Postgres: увидев в плане
Nested Loop на больших таблицах, обычно смотрят, почему не собралась хеш-таблица.
